# Architecture Decision Records

Short records of decisions that are non-obvious or that deviate from the spec. Format: context → decision → consequences.

ADRs still to be written as their steps land: 404 vs 403 for foreign resources (Step 4), derived vs cached balance (Step 5), pessimistic vs optimistic locking (Step 6), idempotency design and no Redis (Step 7).

---

## ADR-001: PostgreSQL with two database roles (least privilege)

**Status:** Accepted (Step 1)

**Context.** The service holds money-shaped data. If an application bug or SQL injection happens, the damage should be limited by the database, not just by Java code.

**Decision.**
- `wallet_owner` owns the schema. Only Flyway connects as it, to run DDL.
- `wallet_app` is the runtime role. It can SELECT/INSERT/UPDATE/DELETE on ordinary tables through default privileges. On the ledger tables it can only SELECT and INSERT.
- Both roles are created by `docker/postgres/init/01-roles.sh`. The Testcontainers base test runs the same script, so tests exercise the same privileges as dev/prod.

**Consequences.** Spring needs two sets of credentials (`spring.datasource.*` and `spring.flyway.*`). Migrations that grant privileges use the Flyway placeholder `${app_role}`. Tests that must bypass triggers (cleanup, or injecting corruption for reconciliation tests) use a separate superuser connection that the app never has.

## ADR-002: Money as BIGINT minor units

**Status:** Accepted (Step 1, schema)

**Context.** Floating point cannot represent 0.10 exactly, so `0.1 + 0.2 != 0.3`. Rounding errors in a ledger are correctness bugs.

**Decision.** Store amounts as `BIGINT` in minor units (paise for INR). In Java, use a `Money` value object with `Math.addExact`/`subtractExact`, which throw on overflow instead of wrapping (Step 2). `ledger_entries.amount` is always positive, and the sign lives in `direction`.

**Consequences.** Every currency needs a known minor-unit exponent (INR = 2). FX rates (Phase 3) are the only place decimals appear, as `NUMERIC(20,10)`, with explicit HALF_EVEN rounding back to minor units.

## ADR-003: Enforce ledger invariants in the database, not only in Java

**Status:** Accepted (Step 1)

**Context.** `LedgerService` will validate that every transaction balances. But a future code path, a manual SQL fix or a bug can bypass the service.

**Decision.**
- A `BEFORE UPDATE OR DELETE` trigger on `transactions` and `ledger_entries` rejects the change (append-only), and REVOKE removes UPDATE/DELETE/TRUNCATE from the app role.
- A `CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY DEFERRED` checks at COMMIT that each transaction has at least one debit and one credit and balances per currency.

Extra guards added beyond the spec, all cheap:
- a statement-level `BEFORE TRUNCATE` trigger, because row triggers don't fire on TRUNCATE;
- a composite FK `(account_id, currency) → accounts (id, currency)`, so a leg can't carry a different currency from its account;
- `CHECK ((type = 'REVERSAL') = (reversal_of_transaction_id IS NOT NULL))` and a no-self-reversal check;
- trigger functions pin `search_path = public`, so they can't be hijacked by an object with the same name in another schema.

**Consequences.** Corrections can only happen by posting reversing entries, so history is never rewritten. The deferred check costs one aggregate query per inserted leg at commit, which is cheap at this scale. Tests can't clean ledger tables as the app role, so test cleanup uses a superuser connection with `session_replication_role = replica`.

## ADR-004: `transactions.idempotency_key_id` — foreign key or not?

**Status:** Accepted (Step 1). This deviates from the spec.

**Context.** The spec lists `idempotency_key_id` as a nullable FK to `idempotency_keys`. It also says idempotency keys have a 24h TTL and are deleted by a daily cleanup job. And `transactions` is append-only.

The ON DELETE options for that FK all fail:
- `NO ACTION` / `RESTRICT`: the cleanup job can't delete any key that produced a transaction, which is most of them. The TTL becomes meaningless and the table grows forever.
- `SET NULL`: this is an UPDATE on `transactions`, so the append-only trigger rejects it and the cleanup fails.
- `CASCADE`: this deletes the money transaction. Unthinkable.

**Decision.** Keep `idempotency_key_id` as a plain `UUID` column with no foreign key. It is a soft reference: while the key exists you can join to it for debugging, and after cleanup it remains a historical identifier.

**Consequences.** The DB doesn't guarantee that the ID pointed to a real key. That's acceptable: the column is diagnostic, and correctness of idempotency is enforced by `UNIQUE (user_id, key)` on `idempotency_keys` at request time, not by this link.

## ADR-005: Schema conventions and migration layout

**Status:** Accepted (Step 1)

- **IDs.** Public IDs are UUIDs generated by the application (v7, time-ordered, so B-tree inserts stay local). Columns have no DB default, so a missing ID fails loudly. `ledger_entries.id` and `audit_log.id` are internal BIGSERIALs, never exposed, and give a total order for keyset pagination.
- **Enumerations** are `TEXT + CHECK`, not Postgres `ENUM`. Adding a value is a constraint swap, not `ALTER TYPE`, and Hibernate maps them as strings.
- **Migration order.** V1 holds the core tables, V2 holds the ledger (transactions, ledger_entries and triggers). The `deposits` table is added in Step 8 because it references `transactions`.
- **`reconciliation_runs.trigger_type`** instead of the spec's `trigger`, to avoid quoting a SQL keyword.
- **`audit_log.actor_user_id`** has no FK, so audit writes never fail on an unknown or anonymous actor (e.g. failed logins).

## ADR-006: Error model (RFC 7807 ProblemDetail with stable codes)

**Status:** Accepted (Step 2)

**Context.** Clients, including the future Next.js BFF, need to react to errors by type, such as showing "insufficient funds" next to the amount field. Human-readable messages change over time, so they can't be parsed. And error bodies must never leak stack traces, SQL or Java class names.

**Decision.**
- Every error is an `application/problem+json` body with the standard fields (`type`, `title`, `status`, `detail`, `instance`), plus:
  - `code`: a stable value from the `ErrorCode` enum. **This is the contract.**
  - `correlationId`: the request's `X-Request-Id`.
  - `errors[]`: `{field, message}` pairs for validation failures.
- Status semantics:
  - **400:** the request is malformed (bad JSON, failed validation, missing header).
  - **422:** the request is well-formed, but a business rule refuses it (`INSUFFICIENT_FUNDS`, `WALLET_FROZEN`, `CURRENCY_MISMATCH`, `SAME_WALLET_TRANSFER`, `IDEMPOTENCY_KEY_REUSED`).
  - **409:** the request conflicts with the current state (`ALREADY_REVERSED`, `IDEMPOTENCY_REQUEST_IN_PROGRESS`).
- Codes added beyond the spec, for Spring's own errors and for bugs: `METHOD_NOT_ALLOWED`, `UNSUPPORTED_MEDIA_TYPE`, `REQUEST_REJECTED` and `INTERNAL_ERROR`.
- Only `ApiException` messages reach the client. Any other exception is logged in full and returned as a generic 500. Jackson parse errors are reduced to the JSON path of the bad field, because their raw messages contain Java type names.
- Boot's fallback `/error` page is set to never include messages, exceptions or stack traces.

**Consequences.** Adding a new error means adding an enum value. The OpenAPI spec (Step 7 checkpoint) will document `ProblemDetail` once and reuse it.

## ADR-007: Correlation ID

**Status:** Accepted (Step 2)

**Decision.** `CorrelationIdFilter` runs first in the filter chain. It reuses the client's `X-Request-Id` only if the value matches `^[A-Za-z0-9._-]{1,64}$`, and otherwise generates a UUID. The ID goes into the logging context (MDC, as `correlationId`), into every log line, into the response header and into error bodies. It is removed from the MDC in a `finally` block, because servlet threads are pooled.

**Why the check.** A client-supplied value containing CR/LF could forge log lines or inject response headers. An unbounded value bloats every log line.

## ADR-008: Authentication: JWT access tokens, rotating refresh tokens, CSRF stance

**Status:** Accepted (Step 3)

**Tokens.**
- **Access token:** a JWT signed with HS256, valid for 15 minutes, with claims `iss`, `sub`, `role`, `iat`, `exp` and `jti`. It is verified without a DB lookup, so every request is cheap.
  - HS256 (one shared secret) rather than RS256 (key pair), because only this service issues *and* verifies tokens; the BFF just forwards them.
  - The decoder accepts only HS256 and our issuer, and requires `exp`. Clock skew tolerance is 30s, using the injected `Clock`.
  - The secret comes from `JWT_SECRET` and must decode to at least 32 bytes, or startup fails.
- **Refresh token:** 256 random bits, opaque, 7-day TTL. Only its SHA-256 hash is stored.

**Rotation and reuse detection.** Each refresh revokes the presented token (`revoked_at`, `replaced_by`) and issues a successor in the same `family_id`. Presenting a revoked token revokes every token in that family and writes `REFRESH_TOKEN_REUSE_DETECTED` to the audit log. The transaction is configured not to roll back on this failure, so the revocation sticks even though the client gets a 401. The token row is read with `SELECT ... FOR UPDATE`, so two concurrent refreshes of the same token are serialized.

**Strictness tradeoff.** Two legitimate parallel refreshes (e.g. two browser tabs) will trip reuse detection and force a re-login. We accept that: the BFF will refresh centrally, and a grace window would be a window for attackers.

**Access tokens can't be revoked.** Logout, logout-all and freezing a user stop *refresh*, but an already-issued access token works until it expires (at most 15 min). This is the price of not checking the DB per request. A denylist keyed on `jti` is possible future work.

**Login.** Every failure returns the same 401 body (no user enumeration). An unknown email still runs one Argon2 verification against a dummy hash, so response time doesn't reveal whether an account exists. The real reason (`UNKNOWN_EMAIL`, `BAD_PASSWORD` or `USER_FROZEN`) is recorded only in the audit log.

**Registration enumeration.** `register` returns `409 EMAIL_ALREADY_REGISTERED` for an existing email, which does reveal that the account exists. Hiding it would need an email-verification flow, which is out of scope. Mitigated by the Phase 3 rate limits.

**Passwords.** Argon2id with m=19 MiB, t=2, p=1 (OWASP minimum) and a 16-byte salt. Length must be 10 to 128 characters. The upper bound limits hashing cost per request.

**CSRF disabled.** CSRF attacks ride on credentials the browser attaches automatically, i.e. cookies. This API authenticates only by an `Authorization: Bearer` header, which a browser never attaches on its own, so a malicious site can't forge an authenticated request. The Next.js BFF *will* hold a browser session cookie, so CSRF protection belongs there.

**Emails** are lower-cased in Java before storing or looking them up. The `citext` column is a backstop: a JDBC `varchar` parameter can make Postgres compare `citext = varchar` as text, which is case-sensitive.
