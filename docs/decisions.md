# Architecture Decision Records

Short records of decisions that are non-obvious or that deviate from the spec. Format: context → decision → consequences.


---

## ADR-001: PostgreSQL with two database roles (least privilege)

**Status:** Accepted (Step 1)

**Context.** The service holds money-shaped data. If an application bug or SQL injection happens, the damage should be limited by the database, not just by Java code.

**Decision.**
- `wallet_owner` owns the schema. Only Flyway connects as it, to run DDL.
- `wallet_app` is the runtime role. It can SELECT/INSERT/UPDATE/DELETE on ordinary tables through default privileges. On the ledger tables it can only SELECT and INSERT.
- Both roles are created by `docker/postgres/init/01-roles.sh`. The Testcontainers base test runs the same script, so tests exercise the same privileges as dev/prod.

**Consequences.** Spring needs two sets of credentials (`spring.datasource.*` and `spring.flyway.*`). Migrations that grant privileges use the Flyway placeholder `${app_role}`. Tests that must bypass triggers (cleanup, or injecting corruption for reconciliation tests) use a separate superuser connection that the app never has.

## ADR-002: Money as BIGINT minor units

**Status:** Accepted (Step 1, schema)

**Context.** Floating point cannot represent 0.10 exactly, so `0.1 + 0.2 != 0.3`. Rounding errors in a ledger are correctness bugs.

**Decision.** Store amounts as `BIGINT` in minor units (paise for INR). In Java, use a `Money` value object with `Math.addExact`/`subtractExact`, which throw on overflow instead of wrapping (Step 2). `ledger_entries.amount` is always positive, and the sign lives in `direction`.

**Consequences.** Every currency needs a known minor-unit exponent (INR = 2). FX rates (Phase 3) are the only place decimals appear, as `NUMERIC(20,10)`, with explicit HALF_EVEN rounding back to minor units.

## ADR-003: Enforce ledger invariants in the database, not only in Java

**Status:** Accepted (Step 1)

**Context.** `LedgerService` will validate that every transaction balances. But a future code path, a manual SQL fix or a bug can bypass the service.

**Decision.**
- A `BEFORE UPDATE OR DELETE` trigger on `transactions` and `ledger_entries` rejects the change (append-only), and REVOKE removes UPDATE/DELETE/TRUNCATE from the app role.
- A `CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY DEFERRED` checks at COMMIT that each transaction has at least one debit and one credit and balances per currency.

Extra guards added beyond the spec, all cheap:
- a statement-level `BEFORE TRUNCATE` trigger, because row triggers don't fire on TRUNCATE;
- a composite FK `(account_id, currency) → accounts (id, currency)`, so a leg can't carry a different currency from its account;
- `CHECK ((type = 'REVERSAL') = (reversal_of_transaction_id IS NOT NULL))` and a no-self-reversal check;
- trigger functions pin `search_path = public`, so they can't be hijacked by an object with the same name in another schema.

**Consequences.** Corrections can only happen by posting reversing entries, so history is never rewritten. The deferred check costs one aggregate query per inserted leg at commit, which is cheap at this scale. Tests can't clean ledger tables as the app role, so test cleanup uses a superuser connection with `session_replication_role = replica`.

## ADR-004: `transactions.idempotency_key_id` — foreign key or not?

**Status:** Accepted (Step 1). This deviates from the spec.

**Context.** The spec lists `idempotency_key_id` as a nullable FK to `idempotency_keys`. It also says idempotency keys have a 24h TTL and are deleted by a daily cleanup job. And `transactions` is append-only.

The ON DELETE options for that FK all fail:
- `NO ACTION` / `RESTRICT`: the cleanup job can't delete any key that produced a transaction, which is most of them. The TTL becomes meaningless and the table grows forever.
- `SET NULL`: this is an UPDATE on `transactions`, so the append-only trigger rejects it and the cleanup fails.
- `CASCADE`: this deletes the money transaction. Unthinkable.

**Decision.** Keep `idempotency_key_id` as a plain `UUID` column with no foreign key. It is a soft reference: while the key exists you can join to it for debugging, and after cleanup it remains a historical identifier.

**Consequences.** The DB doesn't guarantee that the ID pointed to a real key. That's acceptable: the column is diagnostic, and correctness of idempotency is enforced by `UNIQUE (user_id, key)` on `idempotency_keys` at request time, not by this link.

## ADR-005: Schema conventions and migration layout

**Status:** Accepted (Step 1)

- **IDs.** Public IDs are UUIDs generated by the application (v7, time-ordered, so B-tree inserts stay local). Columns have no DB default, so a missing ID fails loudly. `ledger_entries.id` and `audit_log.id` are internal BIGSERIALs, never exposed, and give a total order for keyset pagination.
- **Enumerations** are `TEXT + CHECK`, not Postgres `ENUM`. Adding a value is a constraint swap, not `ALTER TYPE`, and Hibernate maps them as strings.
- **Migration order.** V1 holds the core tables, V2 holds the ledger (transactions, ledger_entries and triggers). The `deposits` table is added in Step 8 because it references `transactions`.
- **`reconciliation_runs.trigger_type`** instead of the spec's `trigger`, to avoid quoting a SQL keyword.
- **`audit_log.actor_user_id`** has no FK, so audit writes never fail on an unknown or anonymous actor (e.g. failed logins).

## ADR-006: Error model (RFC 7807 ProblemDetail with stable codes)

**Status:** Accepted (Step 2)

**Context.** Clients, including the future Next.js BFF, need to react to errors by type, such as showing "insufficient funds" next to the amount field. Human-readable messages change over time, so they can't be parsed. And error bodies must never leak stack traces, SQL or Java class names.

**Decision.**
- Every error is an `application/problem+json` body with the standard fields (`type`, `title`, `status`, `detail`, `instance`), plus:
  - `code`: a stable value from the `ErrorCode` enum. **This is the contract.**
  - `correlationId`: the request's `X-Request-Id`.
  - `errors[]`: `{field, message}` pairs for validation failures.
- Status semantics:
  - **400:** the request is malformed (bad JSON, failed validation, missing header).
  - **422:** the request is well-formed, but a business rule refuses it (`INSUFFICIENT_FUNDS`, `WALLET_FROZEN`, `CURRENCY_MISMATCH`, `SAME_WALLET_TRANSFER`, `IDEMPOTENCY_KEY_REUSED`).
  - **409:** the request conflicts with the current state (`ALREADY_REVERSED`, `IDEMPOTENCY_REQUEST_IN_PROGRESS`).
- Codes added beyond the spec, for Spring's own errors and for bugs: `METHOD_NOT_ALLOWED`, `UNSUPPORTED_MEDIA_TYPE`, `REQUEST_REJECTED` and `INTERNAL_ERROR`.
- Only `ApiException` messages reach the client. Any other exception is logged in full and returned as a generic 500. Jackson parse errors are reduced to the JSON path of the bad field, because their raw messages contain Java type names.
- Boot's fallback `/error` page is set to never include messages, exceptions or stack traces.

**Consequences.** Adding a new error means adding an enum value. The OpenAPI spec (Step 7 checkpoint) will document `ProblemDetail` once and reuse it.

## ADR-007: Correlation ID

**Status:** Accepted (Step 2)

**Decision.** `CorrelationIdFilter` runs first in the filter chain. It reuses the client's `X-Request-Id` only if the value matches `^[A-Za-z0-9._-]{1,64}$`, and otherwise generates a UUID. The ID goes into the logging context (MDC, as `correlationId`), into every log line, into the response header and into error bodies. It is removed from the MDC in a `finally` block, because servlet threads are pooled.

**Why the check.** A client-supplied value containing CR/LF could forge log lines or inject response headers. An unbounded value bloats every log line.

## ADR-008: Authentication: JWT access tokens, rotating refresh tokens, CSRF stance

**Status:** Accepted (Step 3)

**Tokens.**
- **Access token:** a JWT signed with HS256, valid for 15 minutes, with claims `iss`, `sub`, `role`, `iat`, `exp` and `jti`. It is verified without a DB lookup, so every request is cheap.
  - HS256 (one shared secret) rather than RS256 (key pair), because only this service issues *and* verifies tokens; the BFF just forwards them.
  - The decoder accepts only HS256 and our issuer, and requires `exp`. Clock skew tolerance is 30s, using the injected `Clock`.
  - The secret comes from `JWT_SECRET` and must decode to at least 32 bytes, or startup fails.
- **Refresh token:** 256 random bits, opaque, 7-day TTL. Only its SHA-256 hash is stored.

**Rotation and reuse detection.** Each refresh revokes the presented token (`revoked_at`, `replaced_by`) and issues a successor in the same `family_id`. Presenting a revoked token revokes every token in that family and writes `REFRESH_TOKEN_REUSE_DETECTED` to the audit log. The transaction is configured not to roll back on this failure, so the revocation sticks even though the client gets a 401. The token row is read with `SELECT ... FOR UPDATE`, so two concurrent refreshes of the same token are serialized.

**Strictness tradeoff.** Two legitimate parallel refreshes (e.g. two browser tabs) will trip reuse detection and force a re-login. We accept that: the BFF will refresh centrally, and a grace window would be a window for attackers.

**Access tokens can't be revoked.** Logout, logout-all and freezing a user stop *refresh*, but an already-issued access token works until it expires (at most 15 min). This is the price of not checking the DB per request. A denylist keyed on `jti` is possible future work.

**Login.** Every failure returns the same 401 body (no user enumeration). An unknown email still runs one Argon2 verification against a dummy hash, so response time doesn't reveal whether an account exists. The real reason (`UNKNOWN_EMAIL`, `BAD_PASSWORD` or `USER_FROZEN`) is recorded only in the audit log.

**Registration enumeration.** `register` returns `409 EMAIL_ALREADY_REGISTERED` for an existing email, which does reveal that the account exists. Hiding it would need an email-verification flow, which is out of scope. Mitigated by the Phase 3 rate limits.

**Passwords.** Argon2id with m=19 MiB, t=2, p=1 (OWASP minimum) and a 16-byte salt. Length must be 10 to 128 characters. The upper bound limits hashing cost per request.

**CSRF disabled.** CSRF attacks ride on credentials the browser attaches automatically, i.e. cookies. This API authenticates only by an `Authorization: Bearer` header, which a browser never attaches on its own, so a malicious site can't forge an authenticated request. The Next.js BFF *will* hold a browser session cookie, so CSRF protection belongs there.

**Emails** are lower-cased in Java before storing or looking them up. The `citext` column is a backstop: a JDBC `varchar` parameter can make Postgres compare `citext = varchar` as text, which is case-sensitive.

## ADR-009: Someone else's resource returns 404, not 403

**Status:** Accepted (Step 4)

**Context.** A customer requests `GET /wallets/{id}` for a wallet they don't own. A `403 Forbidden` would confirm that the wallet *exists*. That lets an attacker probe IDs and learn which ones are real, the first step of most account-takeover and fraud attempts.

**Decision.**
- **Roles** are checked at the endpoint with capability annotations (ADR-010). A wrong role gets **403**, because the endpoint's existence is public anyway: it's in the OpenAPI spec.
- **Ownership** is checked in the service by *scoping the query*, not by loading and then comparing:
  ```java
  wallets.findByIdAndOwnerUserId(id, caller.id())
         .orElseThrow(() -> ApiException.notFound("Wallet"));
  ```
  "Doesn't exist" and "not yours" are then literally the same code path: the same 404, the same body, and roughly the same timing.
- The owner always comes from the verified JWT (`AuthUser`), never from a path, query or body parameter.
- Customer endpoints (`/api/v1/wallets`, `/transactions`, `/transfers`, ...) always mean **the caller's own** resources, for every role. Staff see other users' data only through `/support` and `/admin` endpoints, which are role-gated and audited.

**Consequences.** Support staff debugging a "wallet not found" can't tell from the response whether the wallet exists. They use the audited support API instead.

## ADR-010: RBAC as capability annotations, with a build-time guard

**Status:** Accepted (Step 4)

**Decision.** There is one annotation per row of the spec's RBAC matrix (`@CanHoldWallets`, `@CanMoveMoney`, `@CanViewAnyUser`, `@AdminOnly`), each a meta-annotation over `@PreAuthorize`. There is no role hierarchy, because ADMIN is not a superset of CUSTOMER: an admin may not move customer money.

**Guard.** `EndpointAccessRulesIT` scans every mapped `/api/v1/**` handler and fails the build if one has no `@PreAuthorize`-based annotation. Exempt are `/auth`, `/me` and `/webhooks`, which are authenticated differently. Without the guard, a forgotten annotation would silently open an endpoint to every logged-in user.

**Why roles come from the JWT, not the DB.** It's cheap: no lookup per request. The cost is that a role change takes effect only when the next access token is issued (at most 15 min later). Freezing a user stops refresh immediately (ADR-008).

**`@PreAuthorize` failures** are thrown inside the controller call, so they reach `@RestControllerAdvice` rather than Spring Security's filter. `GlobalExceptionHandler` maps `AccessDeniedException` to 403 and `AuthenticationException` to 401. Without that, the catch-all handler would turn them into 500s.

## ADR-011: Derived balances only; no cached balance

**Status:** Accepted (Step 5)

**Context.** The spec allows an optional `accounts.cached_balance`, updated in the same transaction as the ledger insert and checked by reconciliation.

**Decision.** Balances are always computed as `SUM(credits) − SUM(debits)` over `ledger_entries` for the account. `cached_balance` exists in the schema but is never written.

**Why.**
- There is exactly one source of truth, so there is no second number that can drift from the ledger.
- Every balance query hits the `(account_id, created_at, id)` index; for a wallet with thousands of entries this is milliseconds.
- The transfer path already holds the wallet's row lock, so computing the SUM under the lock is correct (ADR-012).

**Consequences.** Balance cost grows with a wallet's history. If a wallet reached millions of entries, the next step would be periodic balance snapshots (an append-only table of "balance as of entry N") plus a SUM of the tail, or a cached balance verified nightly. Reconciliation check 4 (cached vs derived) is therefore not applicable.

## ADR-012: Pessimistic row locks in a fixed global order

**Status:** Accepted (Step 6)

**Context.** Fifty concurrent transfers from one wallet must not overspend it, and opposing transfers (A→B and B→A) must not deadlock.

**Decision.**
- Every writer that changes a user wallet's entries (transfer, deposit settlement, reversal, freeze) first takes `SELECT … FOR UPDATE` on the wallet row, through `AccountLocker` only.
- `AccountLocker` sorts IDs by their UUID text, which matches Postgres' `uuid` order, before locking. A cycle of waiters can't form, so there are no deadlocks.
- Balances are checked **after** acquiring the locks, at **READ COMMITTED**. Each statement takes a fresh snapshot, so the SUM sees every write committed before we got the lock. (At REPEATABLE READ the snapshot would predate the lock wait and miss a just-committed debit.)
- System accounts are never locked: nothing checks their balance, and locking EXTERNAL_FUNDING would serialise every deposit platform-wide.

**Alternatives.**
- **Optimistic locking** (`@Version`, retry on conflict): no blocking, but under contention most attempts fail and retry. For a hot wallet that's wasted work and unpredictable latency, plus retry logic in every caller.
- **SERIALIZABLE isolation**: correct without explicit locks, but Postgres aborts conflicting transactions (`40001`), so every money operation needs a retry loop. That's harder to reason about and to test.
- **Single-writer queue per wallet** (Kafka partition per account): scales further, but needs infrastructure the spec rules out (ADR-014).

**Consequences.** Throughput on one wallet is limited to one transfer at a time, which is fine for consumer wallets. Proven by `TransferConcurrencyIT`: 50 parallel transfers yield exactly 10 successes, and 100 opposing ones produce zero deadlocks.

## ADR-013: Idempotency as a service wrapper, with completion in the business transaction

**Status:** Accepted (Step 7)

**Options considered.**
1. **Servlet filter / interceptor + `ResponseBodyAdvice`**: generic and invisible to controllers. But it runs *outside* the business transaction, so "transfer committed" and "key marked COMPLETED" are two separate commits. A crash between them leaves an IN_PROGRESS key; after the 60s takeover, a retry executes the transfer **again**.
2. **`IdempotencyService.execute(caller, key, request, body, operation)` called by each controller**, the one we chose. The operation and the `UPDATE idempotency_keys SET status = 'COMPLETED', response_body = …` run in **one** transaction: both commit or neither does.

**How it works.**
- **Reserve:** `INSERT … ON CONFLICT DO NOTHING` in its own committed transaction, *before* any state change. On conflict:
  - same hash and COMPLETED → replay with `Idempotent-Replayed: true`;
  - different hash → `422 IDEMPOTENCY_KEY_REUSED`;
  - IN_PROGRESS → wait up to 5s polling, then replay or `409`.
- **Request hash:** SHA-256 of method + path + *canonical* JSON (keys sorted), so re-serialised retries match.
- **Business transaction:** first `SELECT … FOR UPDATE` on the key row and confirm `locked_at` is still ours. That value is a fencing token: if a takeover happened, we abort.
- **4xx business errors:** nothing changed, so the ProblemDetail is stored and replayed. On a 5xx the reservation is deleted so the client can retry.
- **Stale takeover:** `UPDATE … WHERE locked_at = <old>`. It blocks while the original still holds the row lock; if the original commits, status is COMPLETED and the takeover matches 0 rows.
- **Missing header:** `@RequestHeader("Idempotency-Key")` is the first controller parameter, so a missing key fails with `400 IDEMPOTENCY_KEY_REQUIRED` before the body is even parsed.

**Guard.** `IdempotencyKeyRequiredIT` lists every mutating endpoint, and fails if a new POST appears without being added (and therefore tested).

**Consequences.** Each controller makes one explicit call: visible, and easy to review. A replayed body is semantically, not byte-for-byte, identical, because JSONB normalises key order.

## ADR-014: No Redis, Kafka or other infrastructure

**Status:** Accepted

Everything the spec needs is done in PostgreSQL:
- **Locks:** row locks.
- **Idempotency store:** a unique index plus `ON CONFLICT`.
- **Job coordination:** ShedLock's JDBC table.
- **Rate-limit windows** (Phase 3): a table.
- **Audit:** an append-only table.

Each extra system would bring its own failure modes, its own consistency gaps with the ledger, and its own operational load. Above all, an idempotency key in Redis can't commit atomically with a ledger insert in Postgres (ADR-013). Redis would be reconsidered for hot-path caching or rate limiting at a scale where Postgres becomes the bottleneck, and measurements would show that first.

## ADR-015: Webhook security

**Status:** Accepted (Step 8)

- **Signature:** `X-Webhook-Signature = hex(HMAC-SHA256(secret, timestamp + "." + rawBody))`, verified over the **raw bytes** (the controller takes `byte[]`) *before* parsing, and compared with `MessageDigest.isEqual` (constant time).
- **Replay protection:** the timestamp is inside the MAC and must be within ±5 min of now. An old captured request can't be replayed, and its timestamp can't be altered.
- **Rotation:** the current and previous secrets are both accepted; every candidate is checked with no early exit.
- **Event idempotency:** `UNIQUE (provider, provider_event_id)` + `ON CONFLICT DO NOTHING`. A PROCESSED duplicate returns 200 without reprocessing.
- **Deposit idempotency:** the deposit row is locked while settling, and an already-SUCCEEDED deposit is a no-op. A *different* event id for the same deposit can't credit twice.
- **Amount check:** the event's amount and currency must equal the deposit's; otherwise it's acknowledged as FAILED and nothing is credited.
- **Forensics:** every request is stored, including forgeries, as REJECTED. Forgeries get a synthetic id (`rejected:<uuid>`) so a forged event can never occupy the id of a real one and make the real delivery look like a duplicate.
- **Status codes:** 401 for bad signature or staleness; 200 for authentic events we can't apply (a retry wouldn't help); 500 only for unexpected errors, so the provider retries.
- **Frozen wallets *are* credited:** the customer's money has already arrived, and freezing blocks spending, not receiving settled funds.

## ADR-016: Reversals instead of edits

**Status:** Accepted (Step 9)

A wrong transaction is corrected by a **REVERSAL** transaction whose legs mirror the original (DEBIT↔CREDIT, same accounts and amounts). The original rows are never touched; the database forbids it (ADR-003).

- **At most one reversal per transaction:** the partial unique index `ux_transactions_reversal_of` enforces it even if two admins race past the Java check. The unique violation is mapped to `409 ALREADY_REVERSED`.
- **A reversal can't be reversed** (`422 REVERSAL_NOT_ALLOWED`). To redo the original effect, post it again as a new transaction, which keeps the story linear and readable.
- **No negative wallets:** if reversing would take a user wallet below zero (the recipient already spent the money), it fails with `422 INSUFFICIENT_FUNDS_FOR_REVERSAL`. Recovering that money is a business process, not a ledger edit.
- **Locking:** affected user wallets are locked in global order (ADR-012).
- **Frozen wallets:** a reversal on a frozen wallet is allowed, because it's a staff correction, not customer spending.
- **Audit:** the reason is required and is stored in the description, the metadata and the audit log.

## ADR-017: Reconciliation on one consistent snapshot

**Status:** Accepted (Step 12)

All checks run in a single **REPEATABLE READ, read-only** transaction, so they see one point-in-time snapshot. Otherwise a transfer committing between "global totals" and "per-transaction balance" could make the two checks disagree and raise a false alarm.

- **Persistence:** the run row is written in separate transactions (RUNNING at the start, then PASSED/FAILED), so a crash still leaves a record.
- **Errors vs warnings:** findings are ERROR or WARNING. Stale PENDING deposits only warn, since they're a provider or customer issue, not a ledger inconsistency.
- **Scheduling:** `@Scheduled` at 02:00 Asia/Kolkata plus ShedLock (`usingDbTime()`), so exactly one instance runs it per night.
- **On failure:** the run logs at ERROR and increments `ledger.reconciliation.mismatches`, which an alert should watch.
- **Testing:** tests inject corruption the only way it could really happen, with a superuser connection and triggers disabled, and assert each check catches it.
